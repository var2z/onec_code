# Задача: локальный MCP-сервер для кода и метаданных 1С

Собрать MCP-сервер в Docker, который индексирует выгрузки конфигураций 1С (zip-архивы из Конфигуратора) и даёт ИИ-агенту структурированный доступ к коду модулей, метаданным и графу зависимостей — быстро и экономно по контексту.

## Контекст
- Windows, Docker Desktop установлен. Python на хосте НЕ ставим — всё внутри контейнера.
- Уже заняты порты 8000 (mcp-1c-v1) и 8001 (1c-syntax-helper). Используй **8002** для MCP и **8003** для веб-интерфейса загрузки; оба порта пробрасываются только на `127.0.0.1`.
- На ПК рядом работают сервер 1С и PostgreSQL (16 ГБ RAM): процессов разбора по умолчанию `ONEC_WORKERS=4`.
- Конфигурации большие (УТ, КА, ERP, Розница, УНФ, БП, БГУ): десятки тысяч .bsl, гигабайты XML. Производительность и размер ответов критичны.
- Архивы лежат в: `D:\mcp-1c-code\inbox`  ← (поправь путь при необходимости)

## Источники данных
- Основной источник — zip-архивы выгрузки конфигурации в файлы из Конфигуратора. Папка `./inbox` монтируется в контейнер **только на чтение** (`:ro`). В ней много архивов; каждый архив = отдельный снимок (snapshot), метка снимка = имя файла без расширения (например `ut_typical`, `ut_klientA`, `roznica3`).
- Архив НЕ распаковывать на диск целиком. Читать через `zipfile` потоково, брать только `.bsl` и нужные XML метаданных (объекты, формы, подписки, регламентные задания, Configuration.xml). Макеты, картинки, справку и прочее пропускать.
- Второй вариант источника — обычная папка-выгрузка (`/DumpConfigToFiles`), тот же парсер.
- Никогда ничего не писать в `inbox` и в папки выгрузки.
- Третий (основной для пользователя) способ — загрузка через веб-интерфейс (см. ниже); такие архивы хранятся в отдельном docker volume `archives`.

## Веб-интерфейс загрузки
- В том же контейнере: FastAPI + одна HTML-страница (без сборщиков фронтенда), порт **8003**, проброс только на `127.0.0.1:8003`, без авторизации.
- Загрузка zip: поле «Название» (произвольный текст, кириллица и пробелы, например «УТ 11.5»; уникально без учёта регистра), выбор файла, кнопка «Загрузить». Потоковая запись на диск, без лимита размера, без чтения файла целиком в память. Прогресс загрузки, затем прогресс индексации по этапам.
- После загрузки проверять, что это выгрузка конфигурации (есть `Configuration.xml`); иначе — понятная ошибка.
- Галочка «Удалить архив после индексации» (по умолчанию выключена). Архивы хранить в docker volume `archives`, не в inbox.
- Таблица снимков: название, имя и версия конфигурации из XML, дата загрузки, размер архива, число модулей/методов, статус (индексируется / готово / ошибка + текст). Действия: переименовать, переиндексировать, удалить (с подтверждением).
- Название из веб-интерфейса = метка снимка. Папка inbox остаётся вторым способом загрузки (метка = имя файла без расширения).
- Индексация — фоновая очередь, по одному снимку за раз; MCP-инструменты во время индексации отвечают по готовым снимкам.

## Шаг 1 — разведка (до написания кода)

- структуру XML: реквизиты, табличные части, синонимы, типы (включая составные), движения документов по регистрам, формы (Form.xml: события формы, элементов, команд), EventSubscriptions, ScheduledJobs, признаки общих модулей (Сервер, ВызовСервера, Клиент, Привилегированный);

## Стек
- Python 3.12, официальный MCP SDK (пакет `mcp`, FastMCP), транспорт streamable HTTP, `0.0.0.0:8002`, путь `/mcp`.
- Хранилище: SQLite (WAL) + FTS5 (tokenizer `unicode61`, регистронезависимо, кириллица) в режиме external content (`content=...`), чтобы тексты не хранились дважды. Neo4j и прочие внешние СУБД не использовать.
- Веб-интерфейс: FastAPI + uvicorn в том же контейнере, порт 8003.
- База индекса — в именованном docker volume, не в папке с архивами.
- `Dockerfile` + `docker-compose.yml`, запуск `docker compose up -d --build`, `restart: unless-stopped`.

## Модель данных
- **snapshots**: метка (имя архива), имя и синоним конфигурации, версия из Configuration.xml, дата архива, дата индексации, статистика.
- **contents**: тексты модулей, хранятся один раз по хешу содержимого (дедупликация между версиями и снимками).
- **files**: snapshot, путь в архиве, CRC32 и размер из zip, ссылка на content.
- **nodes**: (id, snapshot, kind, full_name, parent_id, attrs JSON, content_ref, line_start, line_end).
  Виды узлов: объект метаданных, реквизит, табличная часть и её реквизиты, модуль, метод (процедура/функция), форма, элемент/команда формы, регистр, подписка на событие, регламентное задание.
- **edges**: (from_id, to_id, kind, confidence: exact | heuristic | unresolved | broken, source_location).
  `broken` — связь известна из метаданных/кода, но цель отсутствует (обработчик формы/команды, подписки, регламентного задания на несуществующий метод; `ОбщийМодуль("X")` на несуществующий модуль или метод).
  Модули без исходных текстов (`Module.bin`, `ObjectModule.bin`, `ManagerModule.bin`, модули форм и команд `.bin`): узел модуля создаётся с пометкой «без исходников», методы неизвестны; вызовы, подписки, задания и обработчики форм в такой модуль — `unresolved` на узел модуля с именем метода и причиной, не `broken`.
- **form_elements**: все элементы форм компактно (snapshot, форма, имя, тип, DataPath, родитель), без FTS. Узлы графа — только для элементов с обработчиками и команд форм. Из DataPath основного реквизита формы (`Объект.X`, `Запись.X`, `Объект.ТЧ.X`) — связь «форма → реквизит объекта»; прочие DataPath без связи.
- Индексы: (snapshot, kind, full_name), (from_id, kind), (to_id, kind). FTS по текстам методов и по именам/синонимам объектов.
- Обход графа — `WITH RECURSIVE` с лимитом глубины и защитой от циклов.

## Индексация
- Парсер .bsl: разбить модуль на методы — имя, параметры, Экспорт, директивы компиляции (&НаСервере, &НаКлиенте, &НаСервереБезКонтекста и т.п.), аннотации расширений, область (#Область), строки начала/конца.
  Корректно обрабатывать: вложенные #Если/#Область, комментарии, строковые литералы (в т.ч. многострочные с `|`), ключевые слова внутри строк и комментариев.
- Рёбра:
  - `calls` (метод → метод): `exact` — квалифицированные `ОбщийМодуль.Метод(` и методы своего модуля; `heuristic` — неоднозначные неквалифицированные (поиск среди экспортных методов общих модулей); `unresolved` с пометкой `dynamic` — Выполнить, Вычислить, ОбщегоНазначения.ОбщийМодуль("…"), вызовы по имени в строке, ОписаниеОповещения. Не выдумывать связи.
    - Исключение для `*.ОбщийМодуль("X")` (ОбщегоНазначения, ОбщегоНазначенияКлиент и аналоги): если аргумент — строковый литерал с именем существующего общего модуля и далее вызывается метод — `heuristic` с пометкой `dynamic`. Варианты: цепочка `ОбщегоНазначения.ОбщийМодуль("X").Метод(` и переменная `М = ...ОбщийМодуль("X"); М.Метод(`. Переменная отслеживается только в пределах одного метода; если она переприсваивается — `unresolved`. Нелитеральный аргумент — `unresolved`.
  - Определяемые типы (DefinedType) раскрываются обязательно: в источниках подписок и в типах реквизитов.
  - `event_subscription`: объект-источник → метод-обработчик (с именем события), из EventSubscriptions.
  - `scheduled_job` → метод.
  - `form_handler`: событие формы/элемента/команды → метод модуля формы, из Form.xml.
  - `attr_type`: реквизит → объект по типу ссылки, включая составные типы.
  - `register_records`: документ → регистр (из метаданных); `writes_register`: метод → регистр (Движения.X в коде).
  - `reads_table`: метод → объект/регистр/виртуальная таблица, разбором текстов запросов в коде (`ИЗ` / `СОЕДИНЕНИЕ` `<Тип>.<Имя>[.<ВиртТаблица>]`), confidence `heuristic`.
  - Схемы компоновки данных (макеты типа DataCompositionSchema у любых объектов и общие макеты) индексируются как модули: схема `<Объект>.Макет.<Имя>` (общий макет — `ОбщийМакет.<Имя>.СКД`), набор данных — «метод» с флагом «набор данных», текст — запрос; источники запросов → `reads_table`. Прочие макеты не читаются целиком (тип определяется по началу файла). `who_reads(source=code|dcs)`.
  - `extension_intercepts`: метод расширения → метод основной конфигурации, с типом (&Перед / &После / &Вместо / &ИзменениеИКонтроль).
- Инкрементальность: при `reindex` сравнивать CRC32 и размер файлов в zip с сохранёнными; перечитывать только изменённые и новые, удалять пропавшие. Новый архив — новый снимок; удалённый из inbox архив — удаление снимка из индекса.
- Индексация при старте (если индекса нет) и по инструменту `reindex`. Лог прогресса с этапами и временем.

## Профили конфигураций
- Сервер используется для УТ, КА, ERP, Розницы, УНФ, БП, БГУ, УАТ.
- Универсальная часть — только правила платформы: модули, метаданные, подписки, формы, вызовы, RegisterRecords, `Движения.X`.
- Специфика конфигураций — профили, включаются по имени конфигурации из Configuration.xml. Профиль `up` (УТ/КА/ERP): механизмы проведения `ПроведениеДокументов` (`ЗарегистрироватьУчетныеМеханизмы`, `УчетныеМеханизмыКонфигурации`, `ОтразитьДвижения`, литеральные имена регистров в `ОтразитьДвижения`/`ТребуетсяТаблицаДляДвижений`).
- Неизвестная конфигурация — только универсальная часть, без эвристик чужих профилей. Профиль снимка можно принудительно задать или отключить.
- `who_writes` и `on_write_or_post` показывают применённый профиль и какие связи получены только из RegisterRecords.
- Профили для БП, Розницы, УНФ, БГУ, УАТ добавляются после проверки на их выгрузках.
- Профиль `unf` (УНФ 3): литеральное имя регистра в `ПроведениеДокументовУНФ.ОтразитьДвижения("Регистр", …)` → `writes_register`; `exact`, если регистр в RegisterRecords документа-владельца модуля, иначе `heuristic`.
- Нетиповые конфигурации сторонних разработчиков (например, Айлекс «Торговое предприятие 7») профилей не получают — только универсальная часть.
- БП 3.0 (проверено на БИТ.Финанс поверх БП 3.0.189): отдельного механизма проведения нет — `ОбработкаПроведения` передаёт `Движения` в общие модули (`УчетНДС`, `УчетТоваров`…), это покрывает универсальная часть; профиль не нужен.

## Разрешение имён (важно для удобства)
- Имена объектов и модулей нечувствительны к регистру; принимаются русские и английские типы (Документ/Document, ОбщийМодуль/CommonModule, РегистрНакопления/AccumulationRegister и т.д.), синоним объекта вместо имени, короткие имена модулей (МодульОбъекта, МодульМенеджера, МодульНабораЗаписей, Форма.<Имя>).
  Примеры: `Документ.РеализацияТоваровУслуг.МодульМенеджера`, `ОбщийМодуль.ОбщегоНазначения`, `Документ.РеализацияТоваровУслуг.Форма.ФормаДокумента`.
- Если точного совпадения нет — не возвращать пустоту, а вернуть ближайшие варианты («возможно, вы имели в виду…»).
- Параметр `config` во всех инструментах принимает: метку снимка (без учёта регистра и лишних пробелов: «ут 11.5» = «УТ  11.5»), или имя конфигурации (берётся последняя версия), или `имя@версия`. Если `config` не указан — искать по всем снимкам и в каждом результате явно указывать метку и версию.

## MCP-инструменты
Все ответы компактные, с `limit` и пагинацией. Графовые инструменты возвращают только имена узлов, типы связей, confidence и счётчики — без текстов кода. Тексты — только через get_procedure / get_module.

**Каталог**
- `list_configs()` — снимки, сгруппированные по имени конфигурации: метка, версия, дата, число объектов/модулей/методов.
- `list_objects(query?, object_type?, config?)` — поиск объектов по имени/синониму.
- `get_object(full_name, config?)` — структура объекта: реквизиты (с типами), табличные части, формы, модули, движения по регистрам, подписки на него.

**Код**
- `search_code(query, config?, object_type?, limit=20)` — FTS по коду: снимок, модуль, метод, строка, короткий фрагмент.
- `find_procedure(name, config?, module_hint?)` — поиск метода по имени (точно → префикс → подстрока) во всех модулях; `module_hint` сужает по части имени модуля или синониму объекта. Возвращает кандидатов: снимок, модуль, сигнатура, Экспорт, директива, строки.
- `get_procedure(module, name, config?)` — полный текст одного метода с номерами строк.
- `get_module_outline(module, config?)` — список методов модуля: имя, Экспорт, директива, область, строки.
- `get_module(module, config?, start_line?, end_line?)` — текст модуля кусками, с лимитом строк на ответ.

**Граф**
- `get_dependencies(node, direction=out|in|both, edge_kinds?, depth=1..5, config?)`.
- `find_callers(name, module?, config?)` / `find_calls(module, name, config?)` — с пометкой confidence.
- `who_writes(register, config?)` / `who_reads(object_or_register, config?)`.
- `on_write_or_post(document, event?, depth?, config?)` — что реально выполнится при записи/проведении: обработчики модуля объекта, подписки на события, перехваты расширений, затем вызовы вглубь.
- `impact(node, depth?, config?)` — обратный обход: что затронет изменение объекта/реквизита/метода.
- `call_path(from, to, max_depth?, config?, edge_kinds?)` — кратчайшие пути; по умолчанию только `calls`, можно включить `form_handler`, `event_subscription`, `scheduled_job`, `posting_mechanism`, `writes_register` — путь «команда/кнопка формы → … → запись в регистр».

- `find_broken_refs(config?)` — битые ссылки (confidence=broken): обработчики форм и команд, подписки, регламентные задания, `ОбщийМодуль("X")` на несуществующий модуль/метод. Сначала ссылки метаданных и прямые вызовы; `ОбщийМодуль("X")` на отсутствующие модули (код библиотек для необязательных подсистем, в БП — тысячи) без `kind` свёрнуты в сводку по модулям.
- `find_form_usages(attribute, config?)` — на каких формах выводится реквизит; `get_form_element(form, element, config?)` — к какому реквизиту привязан элемент формы.
- События (подписок, форм, модулей) принимаются и по русскому, и по английскому имени (`ПередЗаписью` = `BeforeWrite`). Русские имена редких событий не угадываются: без подтверждения по справке платформы остаётся английское.

**Версии и сравнение**
- `diff_procedure(module, name, config_a, config_b)` — unified diff одного метода.
- `diff_module(module, config_a, config_b)` — какие методы добавлены/удалены/изменены (без полного текста).
- `diff_configs(config_a, config_b, object_filter?)` — изменённые модули и объекты метаданных (добавленные/удалённые реквизиты и т.п.), с пагинацией.

**Служебные**
- `reindex(config?, full=false)` — инкрементальная (по умолчанию) или полная переиндексация.
- `index_status()` — идёт ли индексация, прогресс, ошибки.
