# onec-code — MCP-сервер для кода и метаданных 1С

Локальный MCP-сервер в Docker. Индексирует выгрузки конфигураций 1С (zip из Конфигуратора или папку
`/DumpConfigToFiles`) и даёт ИИ-агенту структурированный доступ:
- к коду модулей;
- к метаданным;
- к графу связей: вызовы, подписки, обработчики форм, движения, запросы, расширения.

Ответы компактные: графовые инструменты возвращают только имена, виды связей, confidence и счётчики.
Код отдают только `get_procedure` и `get_module`.

- MCP: `http://localhost:8002/mcp` (streamable HTTP).
- Веб-интерфейс загрузки архивов: `http://localhost:8003`.
- Оба порта открыты только на `127.0.0.1`, авторизации нет.

## Сборка и запуск

Нужен Docker Desktop. Python и прочие программы на хосте не нужны.

```bash
docker compose up -d --build
```

- `docker compose ps` — статус контейнера (`healthy`).
- `docker compose logs -f` — лог индексации с этапами и временем.
- `docker compose down` — остановка. Индекс сохраняется в volume `onec-index`, архивы — в `onec-archives`.

| Что | Где |
|---|---|
| Папка с zip-выгрузками | `./inbox` → `/inbox` (только чтение, сервер туда ничего не пишет) |
| Индекс SQLite | volume `onec-index` (`/data/index.db`) |
| Архивы из веб-интерфейса | volume `onec-archives` (`/archives`) |

Удалить индекс полностью: `docker compose down`, затем `docker volume rm onec-index`.
При следующем запуске индекс построится заново.

### Настройки (docker-compose.yml → `environment`)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `ONEC_WORKERS` | `4` | Процессов разбора при индексации. На ПК с сервером 1С и PostgreSQL (16 ГБ) оставьте 2–4: при 4 пик памяти контейнера около 1 ГБ, при 8 — около 2 ГБ, но индексация быстрее. |
| `ONEC_INBOX_SCAN` | `60` | Период проверки inbox, секунд; `0` — только при старте и по `reindex`. |

Чтобы изменить, поправьте значение в `docker-compose.yml`, например `ONEC_WORKERS: "2"`, и выполните
`docker compose up -d`. Пересборка образа не нужна.

## Как получить выгрузку конфигурации

1. В Конфигураторе: **Конфигурация → Выгрузить конфигурацию в файлы…**. Формат — иерархический (по умолчанию).
   То же в пакетном режиме:
   ```bash
   "C:\Program Files\1cv8\8.3.27.xxxx\bin\1cv8.exe" DESIGNER /F "D:\Базы\УТ" /N Администратор /P пароль /DumpConfigToFiles "D:\Выгрузки\ut" -Format Hierarchical
   ```
   Расширение выгружается отдельно: `/DumpConfigToFiles "D:\Выгрузки\ut_ext" -Extension ИмяРасширения`.
2. Упакуйте папку в zip. `Configuration.xml` может лежать в корне архива или внутри одной папки верхнего уровня.
   Подходит любой архиватор: 7-Zip, PowerShell `Compress-Archive`, «Отправить → Сжатая ZIP-папка».
   Кириллические имена в архивах Проводника (cp866) распознаются.
   ```bash
   powershell Compress-Archive -Path D:\Выгрузки\ut\* -DestinationPath D:\mcp-1c-code\inbox\ut_typical.zip
   ```

## Загрузка в индекс

**Веб-интерфейс** (`http://localhost:8003`):
- Порядок: название → файл → «Загрузить». Название — это метка снимка: любой текст, например «УТ 11.5»; уникально без учёта регистра.
- Файл пишется на диск потоком, без лимита размера. После загрузки проверяется, что это выгрузка конфигурации (есть `Configuration.xml`).
- Сначала показывается прогресс загрузки, затем — этапы индексации.
- Галочка «Удалить архив после индексации» экономит место, но тогда переиндексация невозможна — архив придётся загрузить снова.
- В таблице снимков можно переименовать, переиндексировать (Shift+клик — полная переиндексация) или удалить снимок.
  Переименовывать можно и снимки из inbox: снимок привязан к файлу, а не к названию, файл переименовывать не нужно.

**Папка inbox** — второй способ: положите `*.zip` или папку-выгрузку в `./inbox`. Метка снимка — имя файла без
расширения. Новые, изменённые и удалённые архивы подхватываются при старте и раз в `ONEC_INBOX_SCAN` секунд.
Архив, который ещё копируется, не трогается: индексация начинается, когда файл не менялся между двумя проверками
и открывается как zip (до этого в статусе на странице — заметка «жду, пока закончится копирование»).

Индексация идёт в фоне, по одному снимку за раз. MCP в это время отвечает по готовым снимкам.

## Переиндексация

- **MCP-инструмент `reindex(config?, full=false)`**. По умолчанию инкрементальная:
  - сравниваются CRC32 и размер файлов в zip, перечитываются только изменённые;
  - без изменений — меньше секунды;
  - при одном изменённом модуле — около 25 с, из них около 20 с уходит на пересборку графа.

  `full=true` — полный переразбор. `index_status()` показывает прогресс.
- **Веб-интерфейс** — кнопка «Переиндексировать».
- **Командная строка в контейнере:**
  ```bash
  docker exec onec-code python -m onec_code.cli status
  ```
  ```bash
  docker exec onec-code python -m onec_code.cli sizes
  ```
- После обновления сервера (новая версия парсера или графа) затронутые снимки переиндексируются сами при старте.

## Подключение

### Claude Code

```bash
claude mcp add --transport http onec-code http://localhost:8002/mcp
```

Проверка: `claude mcp list` должен показать `onec-code: http://localhost:8002/mcp (HTTP) - ✓ Connected`,
а `/mcp` в сессии — список инструментов.
По умолчанию сервер добавляется только для текущего проекта; для всех проектов — `claude mcp add --scope user …`.

### Приложение Claude Desktop

`claude_desktop_config.json` (`%APPDATA%\Claude\claude_desktop_config.json`) запускает только локальные
stdio-серверы. Поле `url` там не поддерживается. Коннекторы в настройках приложения подключаются из облака
Anthropic, а `localhost` из облака недоступен. Поэтому нужен stdio-мост к `http://localhost:8002/mcp` —
два рабочих варианта.

**Вариант 1 — `mcp-remote` (нужен Node.js; так у вас уже подключены серверы на 8000 и 8001):**

```json
{
  "mcpServers": {
    "onec-code": {
      "command": "npx",
      "args": ["mcp-remote", "http://localhost:8002/mcp"]
    }
  }
}
```

**Вариант 2 — мост внутри контейнера (без Node и Python на хосте):**

```json
{
  "mcpServers": {
    "onec-code": {
      "command": "docker",
      "args": ["exec", "-i", "onec-code", "python", "-m", "onec_code.stdio_proxy"]
    }
  }
}
```

Добавьте блок в существующий `mcpServers` рядом с другими серверами и перезапустите Claude Desktop.
Второй вариант проверен: `initialize`, `tools/list` и `tools/call` через `docker exec -i` работают.
Контейнер при этом должен быть запущен.

## Инструменты

| Группа | Инструменты |
|---|---|
| Каталог | `list_configs`, `list_objects(query?, object_type?, config?)`, `get_object(full_name, config?, section?)` |
| Код | `search_code`, `find_procedure(name, config?, module_hint?)`, `get_procedure(module, name)`, `get_module_outline`, `get_module(module, start_line?, end_line?)` |
| Граф | `get_dependencies(node, direction, edge_kinds?, depth)`, `find_callers`, `find_calls`, `who_writes`, `who_reads`, `on_write_or_post(document, event?, depth?)`, `impact`, `call_path(from, to, edge_kinds?)` |
| Формы и качество | `find_form_usages(attribute)`, `get_form_element(form, element)`, `find_broken_refs(config?, kind?)` |
| Версии | `diff_procedure`, `diff_module`, `diff_configs(config_a, config_b, object_filter?)` |
| Служебные | `reindex(config?, full?)`, `index_status()` |

**Параметр `config`** принимает:
- метку снимка без учёта регистра и лишних пробелов (`ут 11.5` = `УТ  11.5`);
- имя конфигурации из Configuration.xml — берётся последняя версия;
- `имя@версия`.

Без `config` поиск идёт по всем снимкам. Каждый результат помечается `[метка версия]`, одинаковый код
выводится один раз со списком снимков.

**Имена:**
- регистр не важен, типы принимаются по-русски и по-английски;
- вместо имени можно указать синоним;
- модули можно называть коротко.

Примеры:
- `Документ.РеализацияТоваровУслуг.МодульМенеджера`
- `Document.X.ObjectModule`
- `ОбщийМодуль.ОбщегоНазначения`, или просто `ОбщегоНазначения`
- `ОбщегоНазначения.СообщитьПользователю`
- `Документ.X.Форма.ФормаДокумента`
- `Документ.X.Форма.ФормаДокумента.Команды.Провести`
- `Документ.X.Товары.Номенклатура`
- `Реализация товаров и услуг`

Если имя не найдено, в ответе будут ближайшие варианты («возможно, вы имели в виду…»).

**События** принимаются по-русски и по-английски: `ПередЗаписью` = `BeforeWrite`. Для 12 редких событий форм
русское имя не подтверждено справкой платформы, поэтому они показываются по-английски.

**Confidence связей:**
- `exact` — точно;
- `heuristic` (`~`) — выведено эвристикой;
- `unresolved` (`?`) — динамические вызовы: `Выполнить`, `Вычислить`, строки, `ОписаниеОповещения`;
- `broken` (`✗`) — связь известна, а цели нет.

**Схемы компоновки данных (СКД)** — макеты отчётов, обработок, документов и общие макеты типа «Схема компоновки
данных» — индексируются как модули: схема `Отчет.X.Макет.ОсновнаяСхемаКомпоновкиДанных`, каждый набор данных — «метод»,
его текст — запрос. Поэтому:
- `who_reads` показывает и наборы данных СКД (`[СКД]`); `source="dcs"` — только они («какие отчёты читают регистр»),
  `source="code"` — только код;
- `search_code` ищет и по запросам СКД;
- `get_module_outline` — список наборов данных, `get_module` / `get_procedure` — текст запросов;
- `diff_configs` / `diff_module` сравнивают схемы между версиями.

Табличные, текстовые и двоичные макеты не индексируются: читается только начало файла, чтобы понять тип.

**Модули без исходных текстов** (`Module.bin` и т.п., например лицензирование в БИТ.Финанс): модуль виден в
индексе, но текст и методы недоступны. Вызовы в него — `unresolved` с именем метода, не `broken`;
`get_module` сообщает, что исходников нет; `find_callers(name="Модуль.Метод")` находит вызывающих.

**`find_broken_refs`** сначала показывает ссылки метаданных и прямые вызовы. Вызовы `ОбщийМодуль("X")` на модули,
которых нет в конфигурации, — обычно код библиотек (БЗК, БРО, 1С:Документооборот) для необязательных подсистем —
сворачиваются в сводку по модулям; подробно — `kind="calls"`.

**Путь от кнопки до регистра:**
`call_path(from_node="Документ.X.Форма.ФормаДокумента.Команды.ПровестиДокумент", to_node="РегистрНакопления.Y", edge_kinds=["form_handler","calls","posting_mechanism","writes_register"])`.

## Профили конфигураций

Граф строится в две части:

- **Универсальная** — только правила платформы: модули, метаданные, подписки, обработчики форм, вызовы,
  RegisterRecords, `Движения.X` в коде, тексты запросов.
- **Профиль** — эвристики конкретного семейства типовых конфигураций. Включается по имени конфигурации
  из Configuration.xml.

| Профиль | Конфигурации | Что добавляет |
|---|---|---|
| `up` | УправлениеТорговлей, КомплекснаяАвтоматизация, УправлениеПредприятием | Механизмы проведения `ПроведениеДокументов`: документ → `ЗарегистрироватьУчетныеМеханизмы` → `УчетныеМеханизмыКонфигурации` → `<модуль>.ОтразитьДвижения`; регистр по литералу в `ОтразитьДвижения(…, "Регистр")` и `ТребуетсяТаблицаДляДвижений("Регистр")` |
| `unf` | УправлениеНебольшойФирмой | Регистр по литералу в `ПроведениеДокументовУНФ.ОтразитьДвижения("Регистр", ТаблицыДляДвижений, Движения, Отказ)`; `exact`, если регистр есть в RegisterRecords документа, из модуля которого идёт вызов. На УНФ 3.0.14: запись в коде видна у 28 из 29 документов по `ЗапасыНаСкладах` (без профиля — 0) |

Для любой другой конфигурации (БП, Розница, БГУ, УАТ…) применяется только универсальная часть, без
эвристик УТ. `who_writes` и `on_write_or_post` пишут, какой профиль применён и какие движения известны только
из RegisterRecords. Профили для других конфигураций будут добавлены после проверки на их выгрузках.
БП 3.0 проверена (БИТ.Финанс на базе БП 3.0.189): движения пишутся прямыми вызовами общих модулей с передачей
`Движения`, это покрывает универсальная часть, профиль не нужен.

Профиль снимка можно задать вручную: `auto` — по имени конфигурации, `none` — отключить, `up` — принудительно.

```bash
docker exec onec-code python -m onec_code.cli profile ut_typical none
```

На УТ 11.5 без профиля пропадают 1 296 связей «документ → механизм» и 190 связей «метод → регистр по литералу»:
684 069 → 682 583 рёбер. Всё остальное работает.

## Ограничения

- **Динамические вызовы** не разрешаются: `Выполнить`, `Вычислить`, вызов по имени в строке, `ОписаниеОповещения`,
  `Документы[Имя]`, `Движения[Имя]`. Такие связи помечаются `unresolved`: цель показывается, если она однозначна
  по литералу, иначе цели нет.
- **`ОбщийМодуль("X")`** со строковым литералом разрешается как `heuristic`. Переменная отслеживается в пределах
  метода по ближайшему присваиванию. Если по разным веткам `Если` приходят разные модули — `unresolved`.
- **Неквалифицированный вызов** разрешается так:
  - сначала метод своего модуля;
  - затем экспортный метод глобального общего модуля;
  - имена, перекрытые локальной переменной, параметром, реквизитом объекта или реквизитом формы, общим модулем
    не считаются.
- **Тексты запросов разбираются эвристически** (`reads_table`, `heuristic`):
  - учитываются источники в `ИЗ` и `СОЕДИНЕНИЕ`, включая виртуальные таблицы;
  - запросы из схем СКД учитываются; запросы, склеенные в коде из нескольких строк, — нет.
- **Движения:** основной источник — RegisterRecords. В коде видны только `Движения.X` и, в профиле `up`,
  литералы в помощниках проведения. Типовые УТ пишут движения обобщённо, поэтому часть регистров известна
  только из RegisterRecords — это явно указывается.
- **Использование реквизита в коде** по имени статически не определяется. Для таких случаев есть
  `find_form_usages` и `search_code`.
- **Элементы форм:** все хранятся в `form_elements`, кроме вспомогательных (подсказки, контекстные меню,
  дополнения поиска). Связь «форма → реквизит» строится только через основной реквизит формы (`Объект.X`,
  `Запись.X`).
- **Обычные формы** (`Form.bin`) не разбираются. В УТ 11 их нет.
- **Расширения:** связь с основной конфигурацией строится с тем снимком, где больше всего заимствованных
  объектов. Проверено на синтетических примерах.
